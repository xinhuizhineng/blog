四、关键配置文件

4.1 deploy-remote.sh（部署脚本）

位置：scripts/deploy-remote.sh

8 步流程：

步骤操作说明
1/8解压源码tar xzf 到新 release 目录，删除原始包
2/8复制环境变量优先 /tmp/.env.production > shared > current
3/8pnpm install–frozen-lockfile，锁定依赖版本
4/8pnpm buildsource .env.production 后构建
5/8验证 standalone检查 server.js 存在，复制 static + public
6/8切换 current旧 current 存为 previous，新 release 链为 current
7/8PM2 重启删除旧进程，从新 release 的 ecosystem.config.js 启动
8/8健康检查curl 127.0.0.1:3000，2xx 即成功，清理旧 release

失败时输出回滚命令：

九、注意事项

  1. 必须先提交代码：git archive HEAD 只打包已提交代码，未提交的修改不会部署。部署前确保 git status 显示 “working tree clean”。

  2. .env.production 不在 Git 中：.gitignore 的 .env* 规则排除了它。部署脚本从 /tmp/.env.production 读取，每次部署都会上传本地版本。

  3. deploy-remote.sh 随代码一起部署：脚本在 scripts/ 目录下，git archive 会包含它。但实际执行的是上传到 /tmp/deploy-remote.sh 的版本。

  4. TypeScript 类型检查已临时关闭：next.config.ts 中 ignoreBuildErrors: true，遗留类型错误不阻断构建。修复完所有类型错误后改回 false。

  5. 端口统一为 3000：PM2、Nginx proxy_pass、Docker 配置全部使用 3000。

  6. HOSTNAME 强制 0.0.0.0：ecosystem.config.js 中强制设置，避免系统 HOSTNAME（如 ip-172-31-xx-xx）导致应用只绑定内网 IP，健康检查和 Nginx 代理失效。

11.2 Dockerfile 多阶段构建说明

1
2
3

Stage 1: deps        → 安装全量依赖（含 devDependencies），BuildKit 缓存 pnpm store
Stage 2: builder     → 复制源码，pnpm run build:prod，BuildKit 缓存 .next/cache
Stage 3: runner     → Alpine + dumb-init，复制 standalone 产物，非 root 用户运行

关键设计：

  • BuildKit 缓存挂载：pnpm store 和 .next/cache 跨构建复用，增量构建快
  • 依赖层与源码层分离：改代码不重装依赖
  • standalone 模式：镜像不含 node_modules，仅 standalone 追踪的文件
  • outputFileTracingIncludes 已在 next.config.ts 配置 jose 模块
  • dumb-init 作为 PID 1，正确转发 SIGTERM 实现优雅退出

11.3 两种 Docker 部署模式

模式 A：纯容器（复用系统 Nginx + SSL）

Docker 只跑应用容器，SSL 和域名继续用系统 Nginx（与 PM2 方案一致）。

适用场景：服务器已有系统 Nginx + SSL 证书，只想把进程管理从 PM2 换成 Docker。

模式 B：全容器（Docker Nginx + Certbot 自动 SSL）

Docker 管理全部：应用容器 + Nginx 反向代理 + Let’s Encrypt 证书自动签发和续期。

适用场景：全新服务器，不想手动配 Nginx 和 SSL，一切交给 Docker Compose。

11.8 Docker 部署注意事项

  1. 端口冲突：模式 A 和 B 不能同时使用。模式 B 的 Nginx 容器会占用 80/443 端口，与系统 Nginx 冲突。

  2. env.docker 不提交 Git：.dockerignore 已排除 env.docker 和 .docker/env.docker，需要在服务器上手动创建。

  3. git pull 部署 vs git archive 部署：Docker 的 deploy.sh 使用 git pull，需要服务器有仓库访问权限（部署密钥或 HTTPS 认证）。PM2 方案用 git archive 打包上传，不需要服务器访问 Git 仓库。

  4. 数据卷：SSL 证书存在 .docker/certbot/conf/ 目录，Docker 容器重建不会丢失证书。但 docker compose down 删除容器后，目录文件仍在。

  5. 内存限制：docker-compose.yml 配置了 512M 内存上限。如应用 OOM，调整 deploy.resources.limits.memory。

  6. 从 PM2 迁移到 Docker：必须先 pm2 delete stativo 释放端口 3000，否则 Docker 容器端口映射会失败。
